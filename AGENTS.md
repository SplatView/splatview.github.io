# SplatView web contributor instructions

Before adding or changing any feature, read the shared product contract at `../SplatPreview/design/cross-platform-product-contract.md` and its `feature-reviews/TEMPLATE.md`. This is a development-workspace documentation reference, not a build dependency. A standalone checkout uses a reviewed copy pinned by source revision or file digest and records that identity in the feature review. Use the reviewed local bundle in `contracts/product/`, pinned by `contracts/product-adapter.json`; never build against live sibling source.

- Create or amend a feature review in `design/feature-reviews/` before implementation. Review Windows, macOS, Ubuntu and web, plus affected preview/thumbnail hosts. Decide required/conditional/excluded policy from current sources and capabilities, separately from implementation/test status. A missing browser implementation is a gap, not proof of a browser restriction.
- Read `README.md`, `WEB_PORT_PLAN.md`, `IMPLEMENTATION_STATUS.md`, `docs/parity/capabilities-v1.json` and approved UI differences. Preserve source/toolchain locks, generated-asset checks, native/WASM contracts, typed actions, worker/codec budgets and browser tests. New features must pass these existing contracts as well as the shared platform review, including API/CLI decisions, formats, defaults, input, rendering, persistence, background work, tutorials and removals.
- Target viewing and lightweight editing. Separate product exclusions from actual browser APIs/permissions, resource limits and implementation gaps. Advanced web code already exists; do not delete it or silently change shipped behavior as a side effect of a contract review.
- Declare surfaces and runtime requirements explicitly. Web-lite excludes a local agent server and source-overwrite commands. Agent-only measurement has no web UI/tutorial entry. Browser-local saved views do not update operating-system thumbnails, and a download click does not prove disk persistence.
- Preserve concurrent edits and existing state/controller/worker ownership. Do not build against live sibling source or silently refresh frozen desktop/generated inputs. Report the review record, actual checks/failures and browser/OS/GPU/security-context evidence; portable tests alone do not qualify browser behavior.
- Keep modules cohesive and use shared typed contracts across layers. Separate pure geometry/layout/encoding from GPU and native resource lifecycles; retain one explicit owner for submission, cancellation, retirement and publication. Avoid compatibility barrels or speculative frameworks for internal moves. Follow the [selection module map and focused validation workflow](docs/development/selection.md) when changing selection code.

The review workflow applies now. Windows has an automated registration-review gate; the web typed-action/native-command adapter and worker policy gate are now present. Keep the manual platform review and existing source/WASM/browser contracts until that adapter is qualified. Pure formatting/documentation corrections need no new feature record. Do not advertise a planned profile migration as completed.

The local product bundle and normalized inventory adapter are now present. Run `python -B contracts/product/tool.py verify --root .` in addition to all existing port contracts. New/changed registrations require explicit reviewed bindings and all-platform policy, then regenerated local projections; never relax source locks or replace an existing controller/history owner. Testing-enabled native builds and browser source checks run this gate. Native/runtime qualification remains separate.
