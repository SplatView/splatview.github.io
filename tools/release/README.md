# Release evidence tooling

Run from the workspace root with the pinned Node24+ executable. These commands do not build, run tests, launch browsers, change shipping bytes, or attest that observations came from real hardware.

```
node node_modules/typescript/bin/tsc --project tools/release/tsconfig.json
node tools/release/export-schema.ts --output docs/validation/release-evidence.schema.json
node tools/release/export-schema.ts --check
node tools/release/cli.ts --request .build/release-request.json --output .build/new-release-evidence.json
```

Outputs are exclusive: use a fresh path for every diagnostic attempt. CLI exit0 means full-editor acceptance, exit2 means a structurally consistent pending release (possibly with an accepted bounded subset), and exit1 means invalid evidence. Malformed request contracts throw before publication. The generated named schema describes the output bundle and includes the strict request, ledger, source-capture and suite-inventory contracts in `$defs`. Source types are in `types.ts`; runtime shape validation and exported schema share `schema.ts`.

All references contain exact workspace-relative POSIX path, byte count and SHA256. Paths cannot escape the workspace, use reserved/ambiguous names or aliases, or traverse links/reparse redirects. Reads are bounded, compare open-file identity/size/timestamps before and after, reread all bytes, and verify hashes. Complete output trees reject links and unexpected leaves. The native publication directory is never enumerated; only its five known leaves are read. Concurrent hostile mutation cannot be cryptographically prevented by ordinary filesystem APIs; run after source stability on a controlled workspace.

The shipping contract recomputes the current application input descriptor using `tools/web-build.mjs`, verifies the native provenance/output identities, recreates deployment roles/digest, and compares the complete final `dist` inventory, including its manifest and three source maps. Historical hashes cannot substitute for current shipping bytes. The normalized source-capture contains `appInputId`, `deploymentId`, `applicationInputs`, `nativeFiles`, `distribution` and `coveredInputs`; preserve the actual upstream capture/command/source seals among these covered inputs when normalizing existing evidence.

The external expected inventory pins every suite, file, leaf, executable bytes, exact command, report bytes, covered inputs, browser output directory and allowed output leaf. Vitest leaf IDs are fullName, with empty project; globally qualified keys are `<file>::<fullName>`. Playwright keys are `<projectName>::<spec.id>`, including the empty default project. Reports must match the exact inventory, all assertions must pass once, and no report/suite/leaf errors, skips, retries, flaky outcomes or extra leaves may occur. Actual Playwright project `outputDir`, terminal `browserOutputDirectory`, command `--output` and expected complete tree must all agree. `.last-run.json` never establishes success by itself. Every attachment is hashed; required genuine fixture attachments must bind the selected immutable receipt/set ID and complete fixture/source/native identities.

Genuine offline A/B/C evidence additionally requires `fixtureApplicability`, a hash-bound `FixtureApplicability` policy. This field is optional for existing non-fixture requests; non-null fixture evidence cannot omit it. `collectFixtureSource(workspace, supplementPaths, {prefix?, withNative?})` reproduces the exact source universe of `build-offline-fixtures.py`: named root files/trees, externally covered supplemental leaves, offline config and the five known native publication leaves, excluding generated build identity and ignored caches. It never enumerates a public/wasm directory, including staged copies. The policy pins the complete current source inventory; every source difference from the original fixture capture needs its exact before/after identity and attributed reason, and every application/native/covered browser/fixture authority input must remain unchanged. Review metadata provides attribution, not invented human approval.

The fixture adapter independently rereads staged source inventories, permits only exact authored A/B/C main comments and C's single fallback-title replacement, recomputes stage app descriptors and deployment roles/digests, checks all native/public copies and generated descriptors, and checks complete output/map inventories. Physical A/B router bytes must match and C must differ; declared metadata cannot substitute for those bytes. Four recorded build commands must match exact executables, argv, working directory, zero exit, scoped log paths and log bytes. Pinned build-tool artifacts are read through workspace-relative references; Python's historical external executable path remains metadata and its actual preserved copy supplies the byte binding. Every fixture-backed browser case needs externally pinned genuine-input and ownership/cache attachments with the selected set, exact observed local origin, one host PID and all three actual host cohort identities. This acceptance remains local and does not qualify deployed HTTPS.

The CLI allows at most128MiB per file and3GiB aggregate read I/O, covering repeated reads of the current and three approximately80MiB source inventories, pinned executables, shipping/output artifacts and the large offline report. A real combined packet exceeded the earlier2GiB bound; the fixed3GiB bound accommodates its approximately2.6GB charged reads. The stdout summary records bytes actually returned by reads and the maximum aggregate bound; bound errors include observed, attempted and maximum bytes. This validator I/O bound is separate from the application's1GiB resource ledger and does not claim supported scene capacity.

Standard Vitest5 JSON omits observed retry/repeat counts. Such a report can be internally valid but remains pending for qualification. `tools/release-vitest-reporter.ts` now records each assertion's actual retry/repeat/flaky diagnostics and the run outcome through Vitest5.0.3's public reporter API. Run `node node_modules/vitest/vitest.mjs run --reporter=./tools/release-vitest-reporter.ts --outputFile=NEW_EXISTING_PARENT/report.json`. `node tools/release/collect-vitest.ts --output NEW_EXISTING_PARENT/collection.json` independently collects dynamic case declarations without running test bodies. Caller metadata/default configuration is insufficient. Do not add runtime fields retroactively to historical reports.

Each capability-ledger cell names its exact required case keys independently of request bindings. Empty `requiredCaseIds` means that the concrete evidence inventory is still pending; it never qualifies. Bindings must match the ledger exactly and may only name actual inspected cases. Covered-input applicability is also externally pinned; historical evidence needs a hash-bound observed source capture, all covered inputs unchanged in executed/current inventories, and explicit attributed review. Review identity is consistency metadata, not fabricated human approval or execution authentication.

Native, independent format, visual, manual and deployed HTTPS workflows currently remain explicit pending gates until strict reproducible adapters are added. An opaque `status:passed` is rejected by the request contract. Benchmark reports use the existing benchmark validator and an externally mapped shipping build (including actual core/camera WASM hashes), but remain pending for the genuine collector/raw-observation contract. JSON consistency does not establish supported capacity. Operating budget claims are refused, and configuration claims require qualified cells carrying those actual observed configurations. No fixtures, targets, thresholds or measured budgets are manufactured here.

The JSON capability ledger, compact capabilities CSV and original feature CSV must cover the same features exactly once; excluded native integrations need explicit reasons and no required cells. A bounded packet can qualify only its requested, fully matched cells. The full editor remains pending until every retained capability and global browser/host gate qualifies. Mac, Safari and VoiceOver hardware are optional; missing optional hardware cannot block this web-app scope.

All unit packets under `tests/release-*.test.ts` are synthetic policy fixtures. They establish validator behavior, not application performance, hardware compatibility or release acceptance.
